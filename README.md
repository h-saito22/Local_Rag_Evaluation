# Local RAG Evaluation

**機密情報を外部に送らずに社内ナレッジを横断検索する、Local LLM × RAG の構築と比較評価**

社内の設計資料・規程・FAQ・議事録などを、クラウドの LLM に送らずに検索・回答できる RAG を、ローカル環境（MacBook Air／Apple Silicon・メモリ 16GB）だけで構築しました。
そのうえで、**プロンプト・モデルの大きさ・量子化・推論エンジン・LoRA** を1つずつ変えて評価し、用途に合った構成を提案します。

> 文書と QA はすべて架空の会社のものです。実在の会社・人物・製品とは関係ありません。

---

## 結論（用途別のおすすめ構成）

| 用途 | おすすめ構成 | 根拠（48問 qa_v1 / 難問22問 qa_hard） |
|---|---|---|
| **標準（まず導入するなら）** | Ollama ＋ qwen3:4b-q8_0 ＋ qwen3-embedding:0.6b ＋ RAG | 45/48、回答時間 中央値15.1秒・最大26.8秒。量子化3種で最速かつ最も安定。サービスが Ollama 1つで済み運用が簡単 |
| **言い換え・計算を含む難しい質問が多い／速さ重視** | MLX ＋ Qwen3-4B 8bit ＋ **LoRA（RAFT）** ＋ RAG | qa_hard 15 → **20/22**、qa_v1 は 44 → 44（悪化なし）、回答時間 中央値 約2秒 |
| **メモリが少ない PC** | Ollama ＋ qwen3:4b-q4_K_M ＋ RAG | 44/48、ファイル 2.5GB（q8_0 は 4.4GB） |
| **避ける構成** | LoRA のみ（RAG なし）／1.7b | LoRA のみは学習文書の中身を混ぜた答えを作る（qa_v1 で20問）。1.7b は thinking が止まらず1問18分 |

要点は3つです。

1. **知識は RAG、読み方は LoRA。** LoRA は RAG があって初めて効く。RAG なしではどの構成もほぼ答えられない（qa_hard の言い換え 0/18）
2. **推論エンジン（Ollama と MLX）の差は小さい。** 速さ・正答率とも誤差の範囲で、差が大きいのは量子化の選び方（q4 → q8 で回答時間の中央値 21.2 → 15.1秒）
3. **回答時間を決めるのは「1トークンの速さ」より「考える量（生成トークン数）」。** 平均だけでなく中央値と最大を見る必要がある（1問の暴走で平均が逆転する）

## システム構成

```mermaid
flowchart LR
    Q[質問] --> R[retrieve<br/>Chroma 検索 k=2]
    D[(社内文書<br/>data/docs)] -->|分割 200字・重なり20字<br/>埋め込み| C[(Chroma<br/>chroma_db)]
    C --> R
    R -->|資料 2件| G[generate<br/>Local LLM]
    G --> A[回答＋参照ファイル]
    subgraph ローカル（ネットを切っても動く）
      C
      R
      G
    end
```

- 土台は **LangGraph**（retrieve → generate の2ノード）
- 埋め込みと LLM は `select_model.json` の `switch` で切り替える（下の4パターン＋MLX）

| switch | 埋め込み | LLM | 外部に送るもの |
|---|---|---|---|
| Cloud_Cloud（基準） | Gemini | Gemini | 文書・質問・回答のすべて |
| Local_Cloud | qwen3-embedding（Ollama） | Gemini | 質問＋検索結果 |
| Cloud_Local | Gemini | qwen3（Ollama） | 文書・質問 |
| **Local_Local** | qwen3-embedding（Ollama） | qwen3（Ollama） | **なし**（Wi-Fi を切った状態で動作を確認） |
| Local_MLX | qwen3-embedding（Ollama） | Qwen3（mlx_lm.server） | なし |

### 「静かな間違い」を防ぐ仕組み
インデックス（chroma_db）を保存して使い回すと、設定を変えたのに古いインデックスのまま答えてしまう事故が起こり得ます。
そこで、インデックスを作るときに次の値を保存し、起動時に今の設定と照合して、違えば **場所・原因・直し方** を示してエラーで止めます。

- 埋め込みモデル名
- chunk_size / chunk_overlap
- 文書の指紋（全ファイルを名前順に読んだ sha256）

## 動かし方

```bash
# 1. ライブラリ
pip install -r requirements.txt   # Python 3.11 で動作確認

# 2. Ollama のモデル
ollama pull qwen3:4b-q8_0
ollama pull qwen3-embedding:0.6b

# 3. 1問だけ聞く（switch は select_model.json で選ぶ）
python lg2_rag_graph.py

# 4. QA をまとめて評価（結果は results/ に CSV、最後に自動で採点）
python evaluate.py
```

MLX ＋ LoRA で動かす場合は、別のターミナルで mlx_lm.server を起動しておきます。

```bash
python -m mlx_lm server --model Qwen/Qwen3-4B-MLX-8bit --adapter-path adapters/qwen3-4b-raft --port 8080
```

- `select_model.json` の Local_MLX の `"LLM"` は `"default_model"` にする（モデル名を書くと、サーバーはアダプタなしのモデルで答える）
- `max_tokens` は明示する（mlx_lm.server の初期値 512 では thinking の途中で打ち切られる）
- 採用したのは 90 ステップ時点のアダプタ（`0000090_adapters.safetensors` を `adapters.safetensors` にコピー済み）
- select_model.py の ChatOpenAI は `extra_body={"chat_template_kwargs": {"enable_thinking": False}}` で **thinking オフが標準**（10/19 の対照実験以降）

## 評価の方法

### データ（data/README.md に詳細）
| ファイル | 中身 | 使い方 |
|---|---|---|
| data/docs/ | 架空「ミライテック」6部署の文書 | 検索対象 |
| data/qa/qa_v1.csv | 48問＝same / paraphrase（言い換え）/ table（表）/ none（資料にない）× 12 | 基本の評価 |
| data/qa/qa_hard.csv | 22問＝言い換え18（用語・組合せ・換算・否定）＋ none 4（近い資料あり） | LoRA の効果を測る |
| data/lora/ | 架空「サクラ物流」5部署の文書と学習用 QA 150件 | LoRA の学習（評価と別の会社にして、答えを覚える効果を除いた） |

### 指標
| 指標 | 中身 |
|---|---|
| hit@2 / MRR | 答えの根拠の文（evidence）を含むチャンクが何位で取れたか（none は除く） |
| 正答率 | キーワード一致＋「資料に記載がありません」ルール（下） |
| 回答時間 | 検索と回答生成を分けて計測。**中央値と最大**で比べる |
| 生成トークン数・tokens/秒 | 「1トークンの速さ」と「考える量」を分けて見る |

### 採点ルール
- 資料にある質問：キーワードのどれか1つを含めば正解。ただし「資料に記載がありません」を含む（自己矛盾）なら不正解
- 資料にない質問（none）：「資料に記載がありません」だけを返したときのみ正解（関係しそうな文章を足したら不正解）

### 条件
- temperature = 0（同じ条件なら回答は毎回一字一句同じになることを確認。時間だけ変わる）
- プロンプトは「プロンプトの比較」で採用した _05、chunk 200 / overlap 20、k = 2

## 結果

### 1. 検索（qwen3-embedding:0.6b、chunk 200、k=2、qa_v1）
hit@2 = **0.944**（34/36）、MRR = **0.875**。外れた P08・P11 はどちらも言い換えの質問で、回答側では直せない（LoRA でも不正解のまま）。

### 2. プロンプト（qwen3:8b、qa_v1）
| | 変えたところ | 正答 | 一言 |
|---|---|---|---|
| 基準 | ― | 39/48 | 不正解9問はすべて「資料に記載がありません」。うち7問は検索で当たっていた |
| _03 | 1文目「資料だけ」→「主な根拠」 | 35/48 | 改善0問。仮説は支持されなかった |
| **_05（採用）** | 2文目を「同じ意味なら言い回しが違っても答える／関係する内容がない場合に限り『資料に記載がありません』とだけ」 | **43/48** | 改善4問・悪化0問。平均回答時間 25.4 → 21.5秒 |

### 3. モデルの大きさ（qwen3、Ollama、プロンプト _05、qa_v1）
| | 8b | 4b | 1.7b |
|---|---|---|---|
| 正答 | 43 | 44 | 40 |
| 回答時間 中央値 / 最大 | 21.3 / 38.4秒 | 23.6 / 98.4秒 | 4.8 / **1066秒** |
| tokens/秒 | ― | 約28 | 約40 |

4b が 8b より遅いのは1トークンの速さではなく生成した量の差。1.7b は P10 で thinking が止まらず上限の 40960 トークンで回答が空になった。

### 4. 量子化（qwen3:4b、Ollama、qa_v1）
| | q4_K_M | **q8_0** | fp16 |
|---|---|---|---|
| ファイル | 2.5 GB | 4.4 GB（実行時メモリ 5.1 GB） | 約 8 GB |
| 正答 | 44 | **45** | 45 |
| 回答時間 中央値 / 最大 | 21.2 / 84.4秒 | **15.1 / 26.8秒** | 22.1 / 53.4秒 |
| tokens/秒 | 19.7 | 15.7 | 6.4 |
| 生成トークン 中央値 | 409 | 215 | 210 |

1トークンはビット数が少ないほど速いが、q4 は考える量が約2倍になり、合計では q8_0 が最速。q8_0 と fp16 は間違えた問題も同じで、8bit で十分。
仮説：重みの表現が粗いモデルほど thinking が長くなる（1.7b の暴走とも共通）。

### 5. 推論エンジン（qwen3 4b・8bit、qa_v1）
| | Ollama q8_0 | MLX 8bit |
|---|---|---|
| 正答 | 45 | 44 |
| 回答時間 中央値 / 最大 | 15.1 / 26.8秒 | 13.1 / 29.5秒 |
| 生成トークン 中央値 | 215 | 206 |
| tokens/秒（生成時間あたり） | 14.7 | 15.7 |

中央値の差（約13%）は同じ設定で回したときの時間のブレ（約10%）と同程度で、確かな差とは言えない。MLX は別サーバーの起動が必要で、埋め込みは Ollama のままなので2サービスの管理になる → 運用の簡単さで Ollama を推奨。

### 6. LoRA（MLX、Qwen3-4B 8bit、4構成の比較）
学習：RAFT 方式（正解の資料＋関係ない資料を context に入れ、資料の「読み方」と、答えがないときに「資料に記載がありません」とだけ返すことを学ばせる）。
rank 8、scale 20、学習率 1e-5、batch 4、150 ステップ（学習するパラメータは全体の 0.18%）。val loss 3.07 → 0.246（90 ステップで最小）→ 0.264（135）で過学習の入り口と判断し、**90 ステップ**のアダプタを採用。

| 構成 | RAG | LoRA | qa_v1（48問） | qa_hard（22問） | 回答時間 中央値（qa_hard） |
|---|---|---|---|---|---|
| Base | なし | なし | 12 | 4 | ― |
| RAG | あり | なし | 44 | 15 | 約17秒 |
| LoRA のみ | なし | あり | 11 | 3 | ― |
| **LoRA ＋ RAG** | あり | あり | **44** | **20** | **2.5秒** |

- 換算の質問（「3万5千円の本は全額出る？」など）で「資料に記載がありません」に逃げる癖が直った（悪化0問）
- LoRA のみ（RAG なし）は、学習文書の中身（「4月と10月」「7営業日前」「法務部の審査」）を混ぜた答えを作った → **LoRA 単体は危ない**

### 7. thinking オフ（LoRA の効果の切り分け）
LoRA 後は生成トークンが 258 → 20 に減り、thinking をほぼしなくなった。正答率が上がった理由が「読み方を学んだ」のか「thinking をやめた」のかを切り分けるため、元のモデルで thinking だけを止めて比べた（qa_hard、RAG あり）。

| | 正答 | 生成トークン 中央値 | 回答時間 中央値 |
|---|---|---|---|
| 元モデル（thinking あり） | 15 | 258 | 16.6秒 |
| 元モデル（thinking オフ） | 14 | 10.5 | 1.9秒 |
| LoRA | **20** | 20 | 2.5秒 |

→ thinking を止めるだけでは正答率は上がらない。**正答率の向上は LoRA の学習の効果、速さの向上は thinking をしなくなったことによる。**
換算の H10・H13・H17 は、元のモデルでは thinking の有無にかかわらず解けず、LoRA で初めて解けた。

## 評価の限界
- **キーワード採点は甘め。** 結論や数値が間違っていてもキーワードを含めば正解になる例がある（qa_hard の H07・H12）。表記ゆれ（「部長承認」と「部長の承認」）で正しい回答を落とす例もある → LLM 採点で補う予定
- **問題数が少ない。** qa_v1 48問・qa_hard 22問なので、1〜2問の差は誤差の範囲として扱った
- **thinking の条件が混ざっている。** MLX の結果のうち「7. thinking オフ」より前（推論エンジン比較・LoRA の4構成）は thinking あり。Ollama の結果はすべて thinking あり
- **MLX の生成上限が実験によって違う。** 推論エンジン比較（qa_v1）は mlx_lm.server の初期値 512 で回っていた（最長 482 トークンで打ち切りはなし）。それ以降は max_tokens = 4096。Ollama は上限なし
- **検索の外れ（P08・P11）は LoRA では直らない。** 埋め込みモデル・チャンク・k の見直しが必要
- LoRA ＋ RAG は thinking をしなくなるぶん、計算や表の読み違いが出る（qa_v1 の P05・T06）。運用では評価で監視する
